## How a type is defined

A type is a row in `item_types` (`ItemType`), not an enum. Each row carries:

| Column     | Meaning                                                       |
| ---------- | ------------------------------------------------------------- |
| `name`     | Lowercase singular key — `snippet`, `prompt`, …                |
| `icon`     | Lucide icon **name as a string**, resolved to a component in the UI |
| `color`    | Hex string, duplicated as a CSS var in `globals.css`            |
| `isSystem` | `true` for the seven built-ins                                 |
| `userId`   | `null` for system types; set for future user-defined types      |

`@@unique([name, userId])` scopes names per user, so a user could later own a
`snippet` type of their own without colliding with the system one. Because Postgres
treats `NULL`s in a unique constraint as distinct, `prisma/seed.ts` deliberately
**finds-then-updates** the system rows instead of upserting them — an upsert would
insert a duplicate on every run.

`Item.itemType` is `onDelete: Restrict`: a type that is in use cannot be deleted out
from under its items.

### The two color sources

The hex value lives in **two** places and they must agree:

- `item_types.color` in the database (seeded from `SYSTEM_ITEM_TYPES` in `prisma/seed.ts`)
- `--color-<name>` in the `@theme inline` block of [src/app/globals.css](src/app/globals.css#L11-L17)

Only the CSS var is actually used for rendering. The UI never reads `item_types.color`;
it maps the type **name** to a Tailwind class (`text-snippet`, `bg-prompt/10`, …) via
the lookup tables in [src/lib/constants/item-types.ts](src/lib/constants/item-types.ts).
The database column is currently informational.

## Text vs File vs URL

`ContentType` is a Postgres enum on `Item`, separate from the type row. It says
**which content column is authoritative**:

| `contentType` | Types                              | Column read      | Other columns |
| ------------- | ---------------------------------- | ---------------- | ------------- |
| `TEXT`        | snippet, prompt, command, note     | `content`        | null          |
| `FILE`        | file, image                        | `fileUrl` + `fileName` + `fileSize` | null |
| `URL`         | link                               | `url`            | null          |

The mapping from type → `contentType` is **not enforced by the schema**. Nothing stops
a `snippet` row being written with `contentType: URL`. The only place the mapping is
currently applied is one ternary in the seed:

```ts
contentType: item.type === "link" ? "URL" : "TEXT"
```

— which is why the seed has no `FILE` rows at all. There is no constant mapping type
names to content types anywhere in `src/`; item CRUD will need one.

Confirmed against `development`: every type holds exactly one distinct `contentType`,
and no row has a populated column outside its bucket.

## Shared properties

Every item, whatever its type, carries the same envelope:

| Field         | Notes                                                    |
| ------------- | -------------------------------------------------------- |
| `id`          | cuid                                                      |
| `title`       | Required, the only required content-ish field             |
| `description` | Optional, `@db.Text`; shown as the row subtitle           |
| `isFavorite`  | Drives the yellow star and the "Favorites" stat           |
| `isPinned`    | Drives the pin icon and the pinned section on the dashboard |
| `createdAt` / `updatedAt` | `createdAt` drives all "recent" ordering      |
| `userId`      | Every query in `src/lib/db/` is scoped by it              |
| `itemTypeId`  | `Restrict` on delete                                      |
| `tags`        | Many-to-many, `Tag.name` globally unique and **shared across users** |
| `collections` | Many-to-many through `ItemCollection`                     |

Type-specific fields are all nullable columns on the same `items` table — a
single-table design, not per-type tables.

`language` is worth calling out as the odd one: it is nominally shared, but is only
meaningful for `snippet` and `command`.

## Display differences

All type-driven styling comes from six parallel lookup tables in
[src/lib/constants/item-types.ts](src/lib/constants/item-types.ts), each keyed by
`ItemTypeName`:

| Table | Used for |
| --- | --- |
| `ITEM_TYPE_ICONS` | Lucide component (also the source of truth for the type-name union) |
| `ITEM_TYPE_TEXT_CLASSES` | `text-*` — icon color |
| `ITEM_TYPE_BG_CLASSES` | `bg-*/10` — tinted icon tile on item rows |
| `ITEM_TYPE_DOT_CLASSES` | `bg-*` — solid dot for a collection's dominant type |
| `ITEM_TYPE_ACCENT_CLASSES` | `border-l-*` — left accent stripe on cards and rows |
| `ITEM_TYPE_LABELS` | Plural display label — "Snippets", "Prompts", … |
| `ITEM_TYPE_SLUGS` | Route segment, via `getItemTypeHref()` |

`ITEM_TYPE_NAMES` (derived from the icon table's key order) defines the **canonical
order** — snippet, prompt, command, note, file, image, link — used to sort the sidebar
type list and to break ties when ranking a collection's dominant type, so nothing
reshuffles between renders.

### Where the differences actually show up today

- **Sidebar type rows** ([SidebarNav.tsx:175-217](src/components/layout/SidebarNav.tsx#L175-L217)) —
  colored icon, plural label, the user's count, and a `PRO` badge for file/image.
- **Item rows** ([ItemRow.tsx](src/components/dashboard/ItemRow.tsx)) — left accent
  stripe + tinted icon tile in the type's color. Everything else (title, pin, star,
  description, tags, date) is identical across types.
- **Collection cards and dots** — take their accent from the collection's most-used
  type via `rankTypes()` in [src/lib/db/collections.ts](src/lib/db/collections.ts#L14-L30).

**What is not yet differentiated:** the item row renders no content at all — no code
block, no thumbnail, no URL. Nothing reads `content`, `url`, `fileUrl` or `language`
in any component. Per-type *content* rendering (syntax-highlighted code, Markdown,
image preview, copy-to-clipboard for commands, favicon/hostname for links) is entirely
unbuilt.

### Pro gating

`PRO_ITEM_TYPES = ["file", "image"]` and `isProItemType()` exist, but the only consumer
is the `PRO` badge in the sidebar. There is **no route or write gating** — nothing
checks `User.isPro` anywhere.

## Gaps worth knowing before building item CRUD

1. **No type → `contentType` constant.** The mapping lives only in a seed ternary.
   Item creation needs it in `src/lib/constants/item-types.ts` alongside the other tables.
2. **`/items/<slug>` routes do not exist.** The sidebar links to all seven; only
   `/dashboard` and `/profile` are built under `src/app/(app)/`. Same for
   `/collections` and `/collections/[id]`.
3. **`note`, `file` and `image` have never held a row** — no seed coverage, and the
   file/image path depends on R2 which is not wired up.
4. **`item_types.color` and `icon` are dead data.** The UI keys off the type *name*.
   A user-defined type would have a color and an icon in the database that nothing
   can render, since the lookup tables are compile-time constants over a fixed union.
   `isItemTypeName()` and the `note` fallback are the current stopgap.
5. **Type counts vs totals can disagree.** `getItemTypeCounts()` filters to
   `isSystem: true`, so once custom types exist the per-type breakdown will sum to
   less than the item total (already noted on the profile page).
