# Item CRUD Architecture

A design for creating, reading, updating and deleting items — one system covering all
seven types, rather than seven parallel implementations.

> Documentation only — generated by `/research item-crud-research`. Nothing here is
> built yet. Sources: [context/project-overview.md](context/project-overview.md),
> [context/coding-standards.md](context/coding-standards.md),
> [docs/item-types.md](docs/item-types.md),
> [prisma/schema.prisma](prisma/schema.prisma),
> [src/lib/constants/item-types.ts](src/lib/constants/item-types.ts),
> plus the existing auth/profile code as the pattern to match.
>
> _Written: 2026-08-20_

---

## The shape of the problem

Seven types, one `items` table. The types differ in exactly three ways:

1. **Which content column is authoritative** — `content`, `fileUrl`, or `url`
2. **How that content is edited** — code editor, Markdown, file picker, URL field
3. **How that content is displayed** — syntax-highlighted block, prose, image, link card

Everything else — title, description, tags, collections, favorite, pin, ownership,
delete — is identical. So the design puts the shared 90% in one action file and one
route, and isolates the differing 10% in components selected by `contentType`.

The guiding rule, taken from the research prompt: **type-specific logic lives in
components, not in actions.** An action receives an already-validated payload and does
not care which type produced it.

## Layer 1 — Constants: the type table grows two columns

[src/lib/constants/item-types.ts](src/lib/constants/item-types.ts) already holds seven
parallel lookup tables keyed by `ItemTypeName`. CRUD needs two more. Both close gaps
identified in [docs/item-types.md](docs/item-types.md).

```ts
/**
 * Which content column each type writes. The mapping exists today only as a
 * ternary in prisma/seed.ts, which is why the seed has no FILE rows at all.
 */
export const ITEM_TYPE_CONTENT_TYPES = {
  snippet: "TEXT",
  prompt: "TEXT",
  command: "TEXT",
  note: "TEXT",
  file: "FILE",
  image: "FILE",
  link: "URL",
} as const satisfies Record<ItemTypeName, ContentType>;

/** Reverse of ITEM_TYPE_SLUGS: the URL segment back to the type name */
const NAME_BY_SLUG = Object.fromEntries(
  ITEM_TYPE_NAMES.map((name) => [ITEM_TYPE_SLUGS[name], name])
) as Record<string, ItemTypeName>;

/** Narrows an untrusted route param to a known type, or null */
export function itemTypeFromSlug(slug: string): ItemTypeName | null {
  return NAME_BY_SLUG[slug] ?? null;
}

/** Singular label for buttons and headings — "New snippet", not "New snippets" */
export const ITEM_TYPE_SINGULAR_LABELS = {
  snippet: "Snippet",
  prompt: "Prompt",
  /* … */
} as const satisfies Record<ItemTypeName, string>;
```

`ITEM_TYPE_CONTENT_TYPES` is the pivot the whole design turns on. Every branch below —
which Zod schema, which form field, which viewer — is a lookup in this table, never an
`if (type === "snippet")` chain scattered across components.

**Note:** `ITEM_TYPE_LABELS` is already plural ("Snippets"), which suits the sidebar
and the page heading but not a button. Adding singular labels beats calling `.slice(0, -1)`
on a plural.

## Layer 2 — Validation: `src/lib/validation/items.ts`

Follows [src/lib/validation/auth.ts](src/lib/validation/auth.ts): schemas live in one
module because both the client (pre-flight, so a mistake never leaves the browser) and
the Server Action (because the client having checked means nothing) parse the same input.

A **discriminated union on the type name** is the right shape. The form always knows its
type, and the union makes the impossible states unrepresentable — a `link` payload
cannot carry `content`, and TypeScript narrows the action's `data` for free.

```ts
const baseItemSchema = z.object({
  title: z.string().trim().min(1, "Title is required").max(200),
  description: z.string().trim().max(1000).optional(),
  tags: z.array(z.string().trim().toLowerCase().min(1).max(30)).max(10).default([]),
  collectionIds: z.array(z.string().cuid()).default([]),
});

const textItemSchema = baseItemSchema.extend({
  type: z.enum(["snippet", "prompt", "command", "note"]),
  content: z.string().min(1, "Content is required"),
  language: z.string().max(30).optional(),
});

const urlItemSchema = baseItemSchema.extend({
  type: z.literal("link"),
  url: z.url("Enter a valid URL"),
});

const fileItemSchema = baseItemSchema.extend({
  type: z.enum(["file", "image"]),
  fileUrl: z.url(),
  fileName: z.string().min(1),
  fileSize: z.number().int().positive(),
});

export const createItemSchema = z.discriminatedUnion("type", [
  textItemSchema,
  urlItemSchema,
  fileItemSchema,
]);

export const updateItemSchema = createItemSchema.and(
  z.object({ id: z.string().cuid() })
);

export type CreateItemInput = z.infer<typeof createItemSchema>;
```

The action derives `contentType` from `ITEM_TYPE_CONTENT_TYPES[data.type]` rather than
accepting it from the client — otherwise the enum and the type row could be made to
disagree, which is exactly the inconsistency the schema does not currently prevent.

**Tag normalisation belongs here.** `Tag.name` is `@unique` **globally** and tags are
shared across users, so `React` and `react` would become two rows. Lowercasing in the
schema, next to the email `.toLowerCase()` precedent, keeps it in one place.

## Layer 3 — Queries: `src/lib/db/items.ts` (extend)

Read functions stay in `lib/db` and are called **directly from server components** — no
action, no route, no fetch. This is the existing pattern: `getPinnedItems`,
`getRecentItems`, `getItemTypeCounts` are all called straight from
[dashboard/page.tsx](src/app/(app)/dashboard/page.tsx) and
[StatsCards.tsx](src/components/dashboard/StatsCards.tsx).

Two additions:

```ts
/** Every item of one type for the current user, newest first */
export async function getItemsByType(
  type: ItemTypeName,
  options?: { search?: string }
): Promise<ItemListEntry[]>

/** One item with everything the drawer edits, or null if not the user's */
export async function getItemById(id: string): Promise<ItemDetail | null>
```

Both keep the established conventions:

- Read the owner through `getCurrentUserId()` and **return an empty array / null when
  it is null**, rather than throwing. Every existing function does this, and it is
  exactly the signed-out case.
- Scope the `where` by `userId`. `getItemById` puts `userId` in the `where` rather than
  fetching and comparing — a row belonging to someone else is then simply not found.
- Select explicitly via a shared `const` (`ITEM_SELECT`), not `include`.
- Map the database row through a `toX` function that narrows the type name with
  `isItemTypeName()` and falls back to `note`, matching `toDashboardItem`.

`getItemsByType` filters on the **type name**, which means a join through `itemType`:

```ts
where: { userId, itemType: { name: type, isSystem: true } }
```

`isSystem: true` matters. Names are unique per `(name, userId)`, so once custom types
exist a user could own a type also called `snippet`; without the flag their items would
appear on the system snippet page.

### A second view model

`DashboardItem` in [src/types/dashboard.ts](src/types/dashboard.ts) is deliberately thin —
no content, no url, no language — because the dashboard row renders none of it. The
drawer needs all of it. Rather than fattening `DashboardItem` and making every dashboard
query haul content it will not render, add `ItemDetail` in `src/types/items.ts` and keep
the list view model lean.

## Layer 4 — Mutations: `src/actions/items.ts`

One file, every mutation, all Server Actions. Per
[coding-standards.md](context/coding-standards.md): Server Actions for form submissions
and simple mutations; API routes only for webhooks, upload progress, and endpoints a
future mobile/CLI client needs. Item CRUD is none of those.

> **The one exception is file upload.** `file` and `image` need `POST /api/upload` — the
> standards name "file uploads with progress tracking" as route territory, and R2
> presigning does not fit an action. The action still writes the row; the route only
> returns a `fileUrl`. This keeps the mutation path uniform: by the time `createItem`
> runs, a file item is just a payload with three extra strings.

```ts
"use server";

export interface ItemActionState {
  success?: boolean;
  error?: string;
  fieldErrors?: Record<string, string>;
}

export async function createItem(prev, formData): Promise<ItemActionState>
export async function updateItem(prev, formData): Promise<ItemActionState>
export async function deleteItem(id: string): Promise<ItemActionState>
export async function toggleItemFavorite(id: string): Promise<ItemActionState>
export async function toggleItemPinned(id: string): Promise<ItemActionState>
```

`createItem` / `updateItem` take `(prevState, formData)` so they drive `useActionState`,
matching [signInWithCredentials](src/actions/auth.ts#L35) and
[deleteAccount](src/actions/account.ts#L20). The toggles take a plain id — they are
fired from a button, not a form, and have no error state worth threading into the UI
beyond a toast.

### The order of operations in every mutation

Fixed, and each step is load-bearing:

1. **Authenticate** — `getCurrentUserId()`; bail with an error if null.
2. **Parse** — `createItemSchema.safeParse(...)`. Never touch the database with
   unvalidated input.
3. **Authorize the write** — ownership is enforced *in the `where` clause*, not by a
   prior read (below).
4. **Write** — inside a `$transaction` when more than one table is touched.
5. **Revalidate** — `revalidatePath` for the paths this changed.
6. **Return** `{ success }` or `{ error }` — never throw at the client.

This mirrors the ordering rule the rate-limit work established: parse first, then act.

### Ownership without a read-then-write race

```ts
// Not this:
const item = await prisma.item.findUnique({ where: { id } });
if (item?.userId !== userId) return { error: "Not found" };
await prisma.item.update({ where: { id }, data });

// This:
const { count } = await prisma.item.updateMany({
  where: { id, userId },   // ownership is part of the write
  data,
});
if (count === 0) return { error: "Item not found" };
```

`updateMany`/`deleteMany` accept a non-unique `where`, so the ownership check and the
write are one statement. No window between them, and `count === 0` answers "does not
exist" and "is not yours" identically — the same refusal-to-be-an-oracle reasoning that
shapes the sign-in and forgot-password responses.

`updateMany` cannot write nested relations, so an update that changes tags or
collections needs a `$transaction`: an `updateMany` guarded by `{ id, userId }` first,
then the relation writes keyed by id, with the transaction rolled back if the count is 0.

### Relations

- **Tags** — `connectOrCreate` on create, `set` on update (`set: []` clears). The seed
  already uses `connectOrCreate`. Orphaned `Tag` rows are left behind by design;
  nothing owns them, and both `deleteAccount` and `delete-non-demo-users.ts`
  deliberately leave them alone.
- **Collections** — write `ItemCollection` join rows. On update, `deleteMany` the
  item's joins then `createMany` the new set, inside the transaction.

### Revalidation

Every route in `(app)` is `force-dynamic`, and a Server Action already refreshes the
route it was called from — so the list the user is looking at updates without help.
What does *not* update is everything else that counts items:

```ts
revalidatePath("/dashboard");                        // stats, pinned, recent
revalidatePath(`/items/${ITEM_TYPE_SLUGS[type]}`);   // the list itself
// sidebar counts live in the (app) layout:
revalidatePath("/(app)", "layout");
```

The sidebar's per-type counts come from `getItemTypeCounts()` in
[the layout](src/app/(app)/layout.tsx#L21), not the page. Creating an item without
revalidating the layout leaves a stale count next to a list that has already grown —
the most likely first bug in this feature.

### Gating (both currently unimplemented)

Both belong in the action, after the parse and before the write:

- **Pro types** — `isProItemType(data.type)` already exists and is used only for the
  sidebar badge. Nothing checks `User.isPro` anywhere in the codebase.
- **Free-tier cap** — 50 items, 3 collections. A `prisma.item.count({ where: { userId } })`
  before the create.

Doing these in the action rather than the form is the point: the form is a convenience,
the action is the boundary.

## Layer 5 — Routing: how `/items/[type]` works

One dynamic route serves all seven types:

```
src/app/(app)/items/[type]/page.tsx     →  /items/snippets … /items/links
```

It joins the existing `(app)` group, so it inherits the sidebar and top bar from
[layout.tsx](src/app/(app)/layout.tsx) at no cost. Route groups add no path segment.

```tsx
export const dynamic = "force-dynamic";

export default async function ItemsPage({
  params,
  searchParams,
}: PageProps<"/items/[type]">) {
  const { type: slug } = await params;
  const type = itemTypeFromSlug(slug);

  // An unknown slug is a 404, not a fallback. /items/widgets is not a page.
  if (!type) notFound();

  const items = await getItemsByType(type);
  /* … */
}

export async function generateMetadata({ params }: PageProps<"/items/[type]">) {
  const type = itemTypeFromSlug((await params).type);
  return { title: type ? `${ITEM_TYPE_LABELS[type]} · DevStash` : "Not found" };
}
```

`params` is a **Promise** in Next 16 and must be awaited. `PageProps<"/items/[type]">`
is generated into `.next/types` once the route file exists.

### Three things to know about routing as it stands

1. **The sidebar already links to all seven `/items/<slug>` URLs** via `getItemTypeHref()`,
   and every one is currently a 404. So does `/collections`. Building this route makes
   seven dead links live at once.

2. **`typedRoutes` is not enabled.** `next.config.ts` sets only `devIndicators: false`,
   and `Link`'s `href` is plain `Url`, which is why those dead links compile today. The
   `LayoutProps`/`PageProps` globals are generated regardless — that part is always on.
   (An earlier note in the feature history assumed typed routes were rejecting bad
   links; they are not, at present.)

3. **The proxy matcher must be extended.** [src/proxy.ts:22](src/proxy.ts#L22) lists
   `/dashboard` and `/profile` explicitly. Without `"/items/:path*"`, the items pages
   are reachable signed-out — they would render empty rather than leak data, since
   `getCurrentUserId()` returns null, but that is an accident of the query layer, not a
   guard. Add `/items` (and `/collections`, when it lands).

### Why no `/items/[type]/[id]` route

The spec asks for one dynamic route, and the UI guidelines call for
"Drawer Animations — Slide-in for item editing", matching
[dashboard-ui-drawer.png](context/screenshots/dashboard-ui-drawer.png). So detail and
edit are a drawer over the list, deep-linkable through a search param:

```
/items/snippets                    list
/items/snippets?item=<id>          drawer open on that item
/items/snippets?item=new           drawer open on a blank form
```

The page reads `searchParams.item`, fetches with `getItemById` when it is a cuid, and
passes the result to the drawer. Benefits: the list stays mounted behind it, the URL is
shareable, Escape and the back button both close it, and there is exactly one route to
maintain.

A dedicated `/items/[type]/[id]` route is the alternative — better for very long notes,
worse for everything else. It can be added later without disturbing this design, since
the drawer's contents are components, not a page.

`searchParams` is untrusted and arrives as `string | string[]`; `firstParam()` in
[src/lib/search-params.ts](src/lib/search-params.ts) already exists for exactly this.

## Layer 6 — Components: where type-specific logic lives

| Component | Client? | Responsibility | Type-aware? |
| --- | :---: | --- | --- |
| `items/[type]/page.tsx` | server | Resolve slug → type, fetch list + optional detail, compose | Resolves it, passes it down |
| `ItemsHeader` | server | Heading from `ITEM_TYPE_LABELS`, count, "New …" trigger | Label + icon only |
| `ItemList` | server | Map rows, render the empty state | No |
| `ItemRow` | server | One row: accent stripe, icon tile, title, pin/star, tags, date | Styling tables only |
| `ItemActions` | **client** | Favorite, pin, edit, delete triggers; calls the toggles | No |
| `DeleteItemDialog` | **client** | Confirm, then `deleteItem` | No |
| `ItemDrawer` | **client** | Slide-in shell; view ↔ edit mode; syncs the `?item=` param | No |
| `ItemForm` | **client** | Shared fields, `useActionState`, pre-flight parse, error display | **Picks the content field** |
| `fields/TextContentField` | **client** | Content textarea/editor + language select | snippet, prompt, command, note |
| `fields/UrlContentField` | **client** | URL input | link |
| `fields/FileContentField` | **client** | Upload to `/api/upload`, hold `fileUrl`/`fileName`/`fileSize` | file, image |
| `views/TextContentView` | server | Code block or Markdown, copy button | Reads `language` |
| `views/UrlContentView` | server | Hostname, favicon, external link | link |
| `views/FileContentView` | server | Image preview or download row + size | file, image |

### The one branch

Type-specific rendering happens in **one place per direction**, both a table lookup:

```tsx
// ItemForm.tsx
const CONTENT_FIELDS = {
  TEXT: TextContentField,
  URL: UrlContentField,
  FILE: FileContentField,
} as const;

const ContentField = CONTENT_FIELDS[ITEM_TYPE_CONTENT_TYPES[type]];
```

Keying on **`contentType`, not the type name**, is what keeps this at three entries
instead of seven. The four text types share a field; file and image share a field. Where
they genuinely differ *within* a content type — an image preview versus a file download
row, a `bash` default language for commands versus none for notes — the leaf component
takes the type name as a prop and adjusts. That is a small, contained difference, not a
seventh implementation.

### Reusing `ItemRow`

[ItemRow.tsx](src/components/dashboard/ItemRow.tsx) already renders exactly the row this
feature needs and is fully type-driven. It should **move** to `components/items/` and be
imported by the dashboard, not be duplicated. It needs one addition — a slot for
`ItemActions` — and the dashboard can pass nothing there.

### Form mechanics, matching what exists

Two established patterns, and this feature uses the Server Action one:

- **`useActionState` + `SubmitButton`** — [SignInForm](src/components/auth/SignInForm.tsx),
  [DeleteAccountDialog](src/components/profile/DeleteAccountDialog.tsx). Errors render
  inline. `SubmitButton` reads `useFormStatus`, so it must live inside the `<form>`.
- **`fetch` + manual state** — [ChangePasswordForm](src/components/profile/ChangePasswordForm.tsx),
  used only where an API route is the target for future non-web clients.

Also carried over:

- Parse with the shared schema **on the client first**, so an obvious mistake never
  makes a round trip — but the action parses again regardless.
- Errors go **inline** via an error component. Toast is reserved for success, especially
  success followed by navigation. The rate-limit work established this deliberately.
- After a successful create the drawer closes and the list refreshes; after an update
  with nothing to navigate to, reset the form by hand, exactly as `ChangePasswordForm`
  does with `formRef.current?.reset()`.

## What has to be true before this can be built

| Prerequisite | Status |
| --- | --- |
| `ITEM_TYPE_CONTENT_TYPES` constant | Missing — the mapping lives only in a seed ternary |
| Slug → type-name reverse lookup | Missing — `ITEM_TYPE_SLUGS` is one-way |
| `/items/*` in the proxy matcher | Missing — only `/dashboard` and `/profile` |
| `textarea`, `select`, `sheet` UI components | Missing — shadcn CLI, no new npm dependency |
| R2 upload (`file`, `image`) | Not started — `fileUrl` has never been written |
| `User.isPro` checks | None anywhere in the codebase |

**Suggested order:** text types first (four of seven, no new dependency, no upload),
then `link` (trivial — one URL field), then `file`/`image` last, behind R2 and Pro
gating. Each is a working slice.

## Deferred, deliberately

These are real parts of the product but are not required for CRUD to work, and each one
is a decision better made against a working list page:

- **Code editor** — a plain `<textarea>` with a monospace font creates and edits
  snippets fine. CodeMirror/Monaco is a real dependency and a real bundle.
- **Markdown rendering** — notes store Markdown either way; rendering it is a viewer
  concern.
- **Syntax highlighting** — `language` is already stored, unread by anything.
- **Search** — `getItemsByType` takes an `options.search` parameter in this design so
  the signature does not have to change later, but the type list works without it.
- **Collection assignment UI** — the action writes join rows from `collectionIds`; the
  multi-select picker can come with the collections feature.

## Open questions

1. **Does the drawer replace the item detail page permanently, or only for now?** Long
   notes may justify a full page later. The design keeps that door open.
2. **What happens to an item's type after creation — is it editable?** Changing type
   across content types (snippet → link) would orphan `content` and demand a `url`. The
   simplest answer is that type is fixed at creation; the schema does not prevent
   changing it.
3. **Should `command` default `language` to `bash`?** Every seeded command sets it, and
   the field is otherwise noise on that form.
4. **Is there an `/items` index route?** Nothing links to one today. Seven type pages
   plus the dashboard may be enough.
