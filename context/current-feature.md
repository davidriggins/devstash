- Email verification on register (Resend): registration creates an unverified account and mails a single-use link; credentials sign-in refuses an unverified account; an unverified user can ask for a fresh one. `src/lib/auth/verification-token.ts` holds create/consume/cooldown, using NextAuth's existing `VerificationToken` table — `identifier` is the email — so **no migration was needed**. Only the SHA-256 *hash* is stored: the raw token is a bearer credential, and a leaked dump should not hand over working links. Links last 24h, `createVerificationToken` deletes any outstanding one for the address first so only the newest works, and the claim is a `$transaction` of delete-then-update so two simultaneous clicks cannot both pass. There is no `createdAt` on that table, so the 60s resend cooldown reads a token's age backwards off `expires` (`TTL - n`). A spent token reads as `invalid`, including for a legitimate double-click — once the row is gone nothing distinguishes the cases, and keeping it to tell them apart would mean links outliving their single use; the copy says "invalid or already used… if you have verified, just sign in". The link points at `GET /api/auth/verify-email`, **not** a page, because clicking it mutates and a page component must not mutate while it renders; that route redirects to `/verify-email?status=…`, which also stops the token travelling in the address bar, history and referrer. The `(auth)/verify-email` page is then purely presentational over six statuses, four of which show `ResendVerificationForm`; unknown/missing status falls back to `sent`. The sign-in block throws `EmailNotVerifiedError extends CredentialsSignin` with `code`, deliberately placed **after** `bcrypt.compare` — a wrong password keeps the vague "Invalid email or password", so the specific message only reaches someone who already proved they own the credentials and is not an account-existence oracle. That reverses the old "authorize never throws" rule, so its comment changed. `EMAIL_NOT_VERIFIED_MESSAGE` lives in `src/lib/auth/messages.ts` because the action returns it and the page renders it on NextAuth's own `?error=CredentialsSignin&code=…` redirect; `SignInForm` matches on that one constant to decide whether to show the "Send a new verification link" link. A failed send does **not** roll back the account — the route returns `emailSent` and `RegisterForm` routes to `?status=send-failed`, since the account is real and the resend path is the recovery. `POST /api/auth/resend-verification` answers identically for unknown, already-verified, GitHub-only and just-mailed addresses; only a malformed address gets a distinct 400, as that leaks nothing. - Email verification toggle: one switch, `EMAIL_VERIFICATION_ENABLED`, read *only* through `isEmailVerificationEnabled()` in `src/lib/auth/email-verification.ts` — five call sites, one parser, so no two of them can disagree. It exists because Resend still has no verified domain: the `onboarding@resend.dev` sandbox delivers only to the Resend account owner, so every other address could register and then never finish. Parsed **opt-out** — anything but the exact string `"false"` leaves verification **on** — so a missing or misspelt value fails to the secure state rather than silently disabling the check. Server-only: never `NEXT_PUBLIC_`, and the browser is told what happened by a `verificationRequired` field on the register response instead of reading the flag. `RegisterForm` matches on `=== false`, so an older or unexpected response still routes to the check-your-email page. With the flag off, `POST /api/auth/register` stamps `emailVerified` **at create** rather than leaving it null for sign-in to ignore — the difference matters when the flag is turned back on, since stamped accounts keep working and null ones would be locked out; it also skips Resend entirely, so a missing `RESEND_API_KEY` cannot break signup, and reports `emailSent: false` because nothing was in fact sent. The `authorize` gate is `isEmailVerificationEnabled() && !user.emailVerified`, which also lets accounts left unverified by an earlier run sign in. `POST /api/auth/resend-verification` short-circuits to its existing generic response, placed *after* the Zod parse so a malformed address still gets its 400. `GET /api/auth/verify-email` and the `/verify-email` page both redirect to `/sign-in` instead of claiming a token to no effect or showing a status that would be a lie — with the flow off, the only link that can arrive is a stale one, and that account can already sign in.
