# Current Feature: Three-Column Items Grid

## Status

In Progress

## Goals

- Show three item cards per row on large screens, up from the current two
- Stay responsive below that: one column on small screens, two in between
- Match the breakpoint ladder the dashboard already uses, rather than inventing
  a new one for this page
- Leave the dashboard's stacked item list untouched — it shares the component
  but supplies its own layout
- Verify at the breakpoint boundaries, not just at one comfortable width

## Notes

Presentational only. One `className` on one element:
`src/app/(app)/items/[type]/page.tsx:84` currently reads
`grid gap-4 md:grid-cols-2`.

**There is already a precedent to match, and it is the 1/2/3 ladder this asks for:**

| Grid | Classes |
| --- | --- |
| Collections (dashboard) | `grid gap-4 sm:grid-cols-2 lg:grid-cols-3` |
| Stats cards (dashboard) | `grid gap-4 sm:grid-cols-2 lg:grid-cols-4` |
| Items (this page) | `grid gap-4 md:grid-cols-2` |

`sm:grid-cols-2 lg:grid-cols-3` is the obvious answer: it gives the three columns
asked for and brings this page in line with the collections grid instead of adding
a third pattern.

**The sidebar is what makes the breakpoint choice non-obvious.** Viewport width is
not content width — the sidebar takes ~256px plus 48px of padding, and it appears
at `md` (768px), where it is a drawer below that. So:

| Viewport | Sidebar | Main area | At 3 cols |
| --- | --- | --- | --- |
| 767px | drawer (hidden) | ~767px | — (2 cols) |
| 768px | appears | ~464px | — (2 cols, ~220px each) |
| 1024px (`lg`) | visible | ~720px | ~230px per card |
| 1280px (`xl`) | visible | ~976px | ~310px per card |

Two things fall out of that. First, **768px is the tightest point on the page** and
already is today: the sidebar appears at exactly the width where the second column
starts. That is pre-existing, not something this change introduces, but it is worth
looking at while in there. Second, `lg` gives roughly 230px per card, which is the
number to judge in the browser — `ItemCard` lays out horizontally (icon tile,
content, date), so it has a floor that a collection card does not. If 230px looks
broken, `xl:grid-cols-3` is the fallback; decide by looking, not by arithmetic.

The sidebar also collapses to an icon rail, which frees ~200px, but that is client
state and no media query can see it. Container queries could, and that is a bigger
change than this spec wants — noted, not solved.

**No new unit tests.** This touches no server action and no utility, so the `test`
step should come back empty. Verification here is the browser at 640 / 767 / 768 /
1024 / 1280 / 1536px, plus a check that `/dashboard` still stacks its items
full-width.

- Forgot password (reset links): a "Forgot your password?" link on `/sign-in`, a `/forgot-password` request page, an emailed single-use link, and a `/reset-password` page that sets the new password. Reset tokens live in NextAuth's existing `VerificationToken` table, so **no migration was needed** — but that table was already owned by the email verification flow, and sharing it is the whole design problem. Verification stores `identifier` as the bare email, so a reset token doing the same would have collided three ways: `createVerificationToken` deletes every row for an address before issuing, so a reset would silently kill a pending verification link and vice versa; `hasRecentVerificationToken` counts any row for the address, so one flow's cooldown would suppress the other's email; and both look a token up by **hash alone**, which is not namespaced, so either flow would happily spend the other's token. The fix is `password-reset:<email>` as the identifier, every reset query scoped to that prefix, and `src/lib/auth/password-reset-token.ts` as a separate module. Testing then surfaced the *reverse* direction, which the spec had missed: a reset token submitted to `/api/auth/verify-email` would have been found by hash and its identifier read as an email — so `consumeVerificationToken` gained a prefix guard too, returning early **without** deleting, because that row is not its to delete. Both directions were checked at module level: each rejects the other's token and neither destroys the other's row. Token handling deliberately mirrors verification — SHA-256 **hash only**, since the raw token is a bearer credential that here grants a password change; issuing replaces any outstanding link; the claim is a `$transaction` of delete-then-update so two simultaneous submits cannot both win; and the 60s cooldown again reads a token's age backwards off `expires` (`TTL - n`), as that table still has no `createdAt`. TTL is **1 hour**, not verification's 24: a forgotten reset link is worth more to whoever finds it. The link points at a **page**, the opposite of the verification link, and for the opposite reason — clicking it only *reads* the token to decide whether to render the form, so nothing mutates during render and a refresh is harmless; the mutation happens on submit, with the token passed by prop and returned in a request body. `POST /api/auth/forgot-password` answers identically for unknown, GitHub-only (`password === null`, nothing to reset) and just-mailed addresses, with only a malformed address getting a 400; it deliberately swallows errors into that same generic 200 rather than a 500, since a send is only ever attempted for an address that *has* an account and a 500 would answer the question the generic response exists to refuse. **Known hole in that:** an existing address does a cooldown query, a token insert and a full HTTP round trip to Resend before replying, while an unknown one returns after a single query — a timing oracle that partly undoes the identical responses. - Rate limiting for auth (Upstash): a sliding-window limiter over Upstash Redis applied to five entry points — credentials sign-in (5 / 15 min, IP + email), `register` and `forgot-password` (3 / hour, IP), `reset-password` (5 / 15 min, IP) and `resend-verification` (3 / 15 min, IP + email). `src/lib/rate-limit.ts` holds one limits table, one `checkRateLimit`, and `rateLimitResponse` for the 429; counters are namespaced `devstash:ratelimit:<name>` so one IP hitting two endpoints does not share a bucket, and an `ephemeralCache` spares Redis a round trip for an identifier already known to be blocked. Added `@upstash/ratelimit` and `@upstash/redis`; **no migration**, and `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` already existed in both `.env` and `.env.production` — both gitignored, so production's values must be set in Vercel or the limiter silently does nothing. **The ordering rule is the load-bearing design decision:** the check runs *after* the Zod parse and *before* any account lookup, and increments for every well-formed request whatever the outcome. Counting only requests that reach a real account would make a refusal proof the address exists — the exact disclosure the generic responses on `forgot-password` and `resend-verification` were built to refuse. Verified both directions: a malformed address 400s five times and never trips the limit (parse really is first), and register's counter advanced across a `201` and two `409`s before refusing. **The review caught a hole that made the headline goal false.** The first implementation put the sign-in limit in `signInWithCredentials`, the Server Action — but that is only the *form's* path to the credentials endpoint. A direct POST to `/api/auth/callback/credentials`, needing nothing but a CSRF token from the public `/api/auth/csrf`, reaches `authorize` without going near the action: measured at **16 consecutive wrong-password attempts, none limited**, every one returning `302 → CredentialsSignin`. Password brute-forcing was untouched by the feature meant to stop it. The fix moves the check into `authorize` in `src/auth.ts`, which *every* caller of the provider goes through, using the `request` NextAuth passes as `authorize`'s second argument. It **moved** rather than being added, or the UI path would spend two tokens per attempt. There is no response to carry a 429 there, so it throws `RateLimitedError extends CredentialsSignin` with `code = RATE_LIMITED_CODE`, mirroring the existing `EmailNotVerifiedError`; the action translates that code for the form and `/sign-in` translates it on NextAuth's own redirect, so a direct-POST attacker and a form user see the same words. Re-verified: attempts 1–5 `code=credentials`, 6–8 `code=RateLimited`, and a different address on the same IP still allowed. `RATE_LIMITED_MESSAGE` deliberately carries **no duration**, unlike the routes' 429 — a NextAuth error code has no room for one, and the only number available is Upstash's `reset`, which is the end of the current sliding sub-window rather than a full window out, so `Retry-After` can under-promise (a 15-minute limit reported "in a minute" under test). **Deviation from the spec:** it said surface the 429 as a toast; all five forms already render `result.error` inline through `AuthError`, and toast is reserved here for success-after-navigation, so a toast would have put this error somewhere different from every other error on the same form. No client code changed at all. Fail-open was proven twice — once accidentally, when `tsx` did not load `.env` and every call returned `remaining=Infinity`, and once deliberately against a dead Redis host, which logged and allowed through rather than throwing. **Known gaps, all deliberate:** keying sign-in by IP + email does not stop credential stuffing (one password against many addresses from one IP), which the spec's own overview names as a threat — closing it needs a second IP-only limit beyond the spec's table; `register` and `forgot-password` at 3/hour by IP alone means one office or CGNAT range gets three signups an hour; `x-forwarded-for` is only trustworthy because Vercel overwrites it, and local testing set it freely to pick buckets, which is exactly what any non-Vercel origin would allow; and `change-password` / `verify-email` were ruled out of scope at load though both are plausible targets. The pre-existing `forgot-password` timing oracle is untouched. Review also trimmed `getClientIp` and `rateLimitMessage` back to module-private once the action stopped using them. Verified against development throughout, with the one account the register test created deleted by exact email — `db:delete-users --yes` was *not* used, since it would also have taken the GitHub-linked `driggins@esri.com` that exists outside this work.
- Items list view (`/items/[type]`): one dynamic route serving all seven system types, making the seven sidebar links that had always 404'd live at once. The slug resolves back to a type name through a new `itemTypeFromSlug()` in `src/lib/constants/item-types.ts`, built by inverting `ITEM_TYPE_SLUGS` rather than by hand, so the two directions cannot drift. **Review caught a real bug in exactly that helper.** The first version used `Object.fromEntries`, and a plain-object lookup walks the prototype chain: `itemTypeFromSlug("constructor")` returned the `Object` constructor, `"__proto__"` returned `Object.prototype`, and `"toString"`/`"valueOf"`/`"hasOwnProperty"` all returned functions — truthy values that the `?? null` fallback never catches. So `if (!type) notFound()` passed a non-type straight into `getItemsByType()` and `ITEM_TYPE_ICONS[type]`, turning a handful of public URLs into 500s while `/items/widgets` looked fine and made the goal appear met. It is a `Map` now, which has no inherited keys; that also dropped the `as Record<string, ItemTypeName | undefined>` cast, so the fix is smaller than what it replaced. Confirmed against all eight probes. `getItemsByType` in `src/lib/db/items.ts` reuses the existing `ITEM_SELECT` and `toDashboardItem`, returns `[]` when `getCurrentUserId()` is null like every other function there, and pins **`isSystem: true`** in the relation filter — type names are unique per `(name, userId)`, so a user could later own a custom type also called `snippet`, and its items do not belong on the system page. Untestable today, since custom types cannot be created in the UI. The page sits in the existing `(app)` group, inheriting the sidebar and top bar at no cost, and is `force-dynamic` like `/dashboard` and `/profile`. **`ItemCard` is the old `ItemRow`, moved rather than duplicated — decided at spec time, not during implementation.** It already drew the type-colored left border and tinted icon tile from the constants tables, and it sets no width and no layout container of its own, so row-versus-card is entirely the parent's decision: the dashboard keeps `space-y-3`, this page uses `grid gap-4 md:grid-cols-2`. Forking would have meant two files sharing four styling tables by hand, the failure those tables exist to prevent. Three changes rode along with the move: the description is `line-clamp-2` instead of `truncate`, since a grid column is narrower and one line loses most of it; it is guarded with `{item.description && …}` because the column is nullable and an empty `<p>` still takes its `mt-1` (the one addition beyond the spec); and an optional `actions` slot sits next to the date for the favorite/pin/delete controls the CRUD feature will add, so that feature need not reopen this file. `src/proxy.ts` gained `/items` and `/items/:path*` — signed out these pages render empty rather than leak, but only because `getCurrentUserId()` returns null, which is a property of the query layer and not a guard. The empty state deliberately carries **no call to action**: there is still no way to create an item, and a button that does nothing is worse than none, so it reads "Notes you add will appear here." rather than "Create your first note". No migration, no new npm dependency, `package.json` untouched. Verified in the browser against development (`ep-green-truth-aylaseez`, confirmed by the environment badge): all seven pages with counts matching the sidebar exactly (4/3/5/0/0/0/6), the empty state on notes, files and images, two columns at 1280px and one at 640px, each type's own accent color, `/items/widgets` returning HTTP 404, the signed-out redirect round-tripping through `callbackUrl` back to `/items/snippets`, and the dashboard rendering unchanged after the component move. **Known gaps, all deliberate:** `getItemsByType` has no `take`, so a Pro account with thousands of items loads all of them — bounded in practice only by the 50-item free tier, and pagination was not in the spec; the `"Not found · DevStash"` string in `generateMetadata` is dead, because `notFound()` hands the title to the not-found boundary (the observed 404 title was plain `DevStash`), but the ternary still needs a branch for type-narrowing; `DashboardItem` is now a misnomer, used by a component and a page that are not the dashboard, left alone rather than churning five files for no behaviour change; and the singular `"1 item"` branch is untested, since no type holds exactly one. A dev-only `TypeError` about a negative performance timestamp appears in the console on the 404 — React's profiling instrumentation reacting to the thrown `notFound()`, absent from production builds. That was **not** confirmed against a production build on purpose: `next start` loads `.env.production`, which points at the production Neon branch. Two process notes: a dev server for this directory was already running from outside the session and Next 16 refuses a second, so testing reused it; and the review step was run without Playwright at request, with the prototype-chain bug proved in plain `node` instead, which was faster and more conclusive than a browser check would have been.
- Vitest for server actions and utilities: one dependency, a Node environment, and no component tests — components are verified in the browser, which is where their real failures show up, and skipping them meant skipping jsdom entirely. `vitest.config.mts` is `.mts` because the config is ESM and the project has no `"type": "module"` (which Next would rather it did not have); `next-auth` and `@auth/core` are inlined through `server.deps.inline`, because Node cannot resolve `next/server` from inside an externalised dependency and the action tests fail to load without it; and the `@/*` alias is written by hand rather than adding `vite-tsconfig-paths` for one line. **`vitest.setup.ts` deletes `DATABASE_URL`**, which matters more than it looks: `src/lib/prisma.ts` throws at import time without it, so an unmocked Prisma import fails loudly instead of opening a connection to Neon. Vitest does not load `.env` the way Next does, so this was already true by accident — stating it makes it a guarantee, and this project's `.env` has pointed at the production branch before. Proved rather than assumed, with a throwaway test asserting that importing `@/lib/prisma` rejects. Tests are colocated as `*.test.ts` and import from `vitest` explicitly rather than enabling globals, so the app's type environment is untouched; they live under `src/`, so `next build` typechecks them too, which is a feature. 63 tests across 7 files in ~1.3s. Several encode regressions already paid for once: the padded `"  padded@test.com  "` that used to 400, the absolute *and* protocol-relative URLs `safePath` must reject, the opt-out parsing where `"flase"` leaves email verification **on**, and the prototype-chain trap in the type lookups. Action tests mock `@/auth`, `@/lib/db/user` and `@/lib/prisma`, and cover what is actually load-bearing: that `callbackUrl` is re-sanitised server-side because the hidden field arrives from the client, that `EMAIL_NOT_VERIFIED_CODE` and `RATE_LIMITED_CODE` are translated while a plain refusal stays vague, that a non-`AuthError` is rethrown so `NEXT_REDIRECT` can complete, that `deleteAccount` re-checks the typed confirmation, and that it deletes items → own item types → user in one transaction. **The suite found a real bug on its first run.** `isItemTypeName` used `name in ITEM_TYPE_ICONS`, and `in` walks the prototype chain, so `isItemTypeName("constructor")` returned `true` and TypeScript then narrowed it to `ItemTypeName`.
