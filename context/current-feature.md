# Current Feature: Items List View

## Status

In Progress

## Goals

- Add the dynamic route `/items/[type]`, serving all seven types from one page
  (`/items/snippets`, `/items/prompts`, `/items/commands`, `/items/notes`,
  `/items/files`, `/items/images`, `/items/links`)
- Resolve the URL slug back to a type name; an unknown slug is a 404, not a fallback
- Fetch the current user's items filtered by that type, newest first
- Render them as a responsive grid of `ItemCard` components — one column on small
  screens, two on medium and up
- Give each card a left border in its item type's color
- Show an empty state when the type holds nothing
- Follow the existing patterns: query in `lib/db`, called directly from a server
  component; no new npm dependencies

## Notes

Read-only. No create, update or delete in this spec — see
@docs/item-crud-architecture.md for how mutations are meant to land later.

**Prerequisites the research turned up:**

- `ITEM_TYPE_SLUGS` in `src/lib/constants/item-types.ts` is **one-way** (name → slug).
  The route needs the reverse lookup, e.g. an `itemTypeFromSlug()` helper alongside it.
- `src/proxy.ts` matches only `/dashboard` and `/profile`. Without `/items/:path*`
  these pages are reachable signed out — they would render empty rather than leak,
  since `getCurrentUserId()` returns null, but that is an accident of the query layer,
  not a guard.

**Constraints:**

- The sidebar already links to all seven `/items/<slug>` URLs via `getItemTypeHref()`,
  and every one is a 404 today. This feature makes all seven live at once.
- Put the route in the existing `(app)` group so it inherits the sidebar and top bar
  from `src/app/(app)/layout.tsx` at no cost. Route groups add no path segment.
- `params` is a Promise in Next 16 and must be awaited. `PageProps<"/items/[type]">`
  is generated once the route file exists.
- `force-dynamic`, like `/dashboard` and `/profile` — this reads live per-user state.
- Filter by type through the relation with `isSystem: true` in the where clause. Names
  are unique per `(name, userId)`, so once custom types exist a user could own a type
  also called `snippet` and their items would otherwise appear on the system page.
- `getItemsByType` should return `[]` when `getCurrentUserId()` is null, matching every
  existing function in `src/lib/db/`.

**`ItemCard` is the existing `ItemRow`, moved — decided, not open.** Do not write a
second component. `src/components/dashboard/ItemRow.tsx` already renders
`rounded-xl border-l-4 bg-card p-4 ring-1` with the type-colored left border this spec
asks for, the tinted icon tile, and four of the six lookup tables already wired. It
sets **no width and no layout container of its own** — the dashboard supplies
`space-y-3`, this page supplies `grid gap-4 md:grid-cols-2`. Row versus card is the
parent's decision; the child is identical either way, so there is nothing to fork.

Duplicating would mean two files importing `ITEM_TYPE_ACCENT_CLASSES`,
`ITEM_TYPE_BG_CLASSES`, `ITEM_TYPE_TEXT_CLASSES` and `ITEM_TYPE_ICONS`, kept visually
in sync by hand — the failure the constants tables exist to prevent.

The work:

- Move `src/components/dashboard/ItemRow.tsx` → `src/components/items/ItemCard.tsx`,
  renaming the component, and update the import in
  `src/components/dashboard/ItemsSection.tsx`. The dashboard keeps using it unchanged.
- Description goes from `truncate` to `line-clamp-2` — better in a narrow grid column,
  and an improvement on the dashboard too.
- Leave an `actions` slot (a `ReactNode` prop defaulting to nothing) for the future
  favorite / pin / delete controls, so the CRUD feature does not have to reopen this.

Revisit only if the card later needs a content preview the dashboard row must not show
— a code excerpt or an image thumbnail. Plausible, but speculative today; a `preview`
prop or a split at that point is cheap. Do not pre-pay for it.

**Empty states matter more than usual here.** On the development branch, `note`, `file`
and `image` hold **zero** items, so three of the seven pages are empty on arrival even
for the demo account. Files and Images are also Pro-only and have no gating anywhere in
the codebase yet; this spec does not add any.

- Forgot password (reset links): a "Forgot your password?" link on `/sign-in`, a `/forgot-password` request page, an emailed single-use link, and a `/reset-password` page that sets the new password. Reset tokens live in NextAuth's existing `VerificationToken` table, so **no migration was needed** — but that table was already owned by the email verification flow, and sharing it is the whole design problem. Verification stores `identifier` as the bare email, so a reset token doing the same would have collided three ways: `createVerificationToken` deletes every row for an address before issuing, so a reset would silently kill a pending verification link and vice versa; `hasRecentVerificationToken` counts any row for the address, so one flow's cooldown would suppress the other's email; and both look a token up by **hash alone**, which is not namespaced, so either flow would happily spend the other's token. The fix is `password-reset:<email>` as the identifier, every reset query scoped to that prefix, and `src/lib/auth/password-reset-token.ts` as a separate module. Testing then surfaced the *reverse* direction, which the spec had missed: a reset token submitted to `/api/auth/verify-email` would have been found by hash and its identifier read as an email — so `consumeVerificationToken` gained a prefix guard too, returning early **without** deleting, because that row is not its to delete. Both directions were checked at module level: each rejects the other's token and neither destroys the other's row. - Rate limiting for auth (Upstash): a sliding-window limiter over Upstash Redis applied to five entry points — credentials sign-in (5 / 15 min, IP + email), `register` and `forgot-password` (3 / hour, IP), `reset-password` (5 / 15 min, IP) and `resend-verification` (3 / 15 min, IP + email). `src/lib/rate-limit.ts` holds one limits table, one `checkRateLimit`, and `rateLimitResponse` for the 429; counters are namespaced `devstash:ratelimit:<name>` so one IP hitting two endpoints does not share a bucket, and an `ephemeralCache` spares Redis a round trip for an identifier already known to be blocked. Added `@upstash/ratelimit` and `@upstash/redis`; **no migration**, and `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` already existed in both `.env` and `.env.production` — both gitignored, so production's values must be set in Vercel or the limiter silently does nothing. **The ordering rule is the load-bearing design decision:** the check runs *after* the Zod parse and *before* any account lookup, and increments for every well-formed request whatever the outcome. Counting only requests that reach a real account would make a refusal proof the address exists — the exact disclosure the generic responses on `forgot-password` and `resend-verification` were built to refuse. Verified both directions: a malformed address 400s five times and never trips the limit (parse really is first), and register's counter advanced across a `201` and two `409`s before refusing. **The review caught a hole that made the headline goal false.** The first implementation put the sign-in limit in `signInWithCredentials`, the Server Action — but that is only the *form's* path to the credentials endpoint. A direct POST to `/api/auth/callback/credentials`, needing nothing but a CSRF token from the public `/api/auth/csrf`, reaches `authorize` without going near the action: measured at **16 consecutive wrong-password attempts, none limited**, every one returning `302 → CredentialsSignin`. Password brute-forcing was untouched by the feature meant to stop it. The fix moves the check into `authorize` in `src/auth.ts`, which *every* caller of the provider goes through, using the `request` NextAuth passes as `authorize`'s second argument. It **moved** rather than being added, or the UI path would spend two tokens per attempt. There is no response to carry a 429 there, so it throws `RateLimitedError extends CredentialsSignin` with `code = RATE_LIMITED_CODE`, mirroring the existing `EmailNotVerifiedError`; the action translates that code for the form and `/sign-in` translates it on NextAuth's own redirect, so a direct-POST attacker and a form user see the same words. Re-verified: attempts 1–5 `code=credentials`, 6–8 `code=RateLimited`, and a different address on the same IP still allowed. `RATE_LIMITED_MESSAGE` deliberately carries **no duration**, unlike the routes' 429 — a NextAuth error code has no room for one, and the only number available is Upstash's `reset`, which is the end of the current sliding sub-window rather than a full window out, so `Retry-After` can under-promise (a 15-minute limit reported "in a minute" under test). **Deviation from the spec:** it said surface the 429 as a toast; all five forms already render `result.error` inline through `AuthError`, and toast is reserved here for success-after-navigation, so a toast would have put this error somewhere different from every other error on the same form. No client code changed at all.
